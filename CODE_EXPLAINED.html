One governed agent, multiple partners

A natural-language request is classified, routed to exactly one configured partner, planned against that partner's live MCP tools, checked for write approval, executed, and summarized from returned evidence.

1. The mental model

The system is a coordinator around an LLM. The model handles fuzzy language decisions; ordinary code owns partner selection, limits, approval, execution, and response contracts.

OpenAI

Interpreter and planner

Produces a strict route, chooses only from live tools, and converts MCP results into a readable answer.

LangGraph

Traffic controller

Moves state through deterministic nodes, repeats bounded planning rounds, and stops unapproved writes.

Partner MCP

Capability boundary

The selected Notion or Linear server advertises tools and performs the actual operation with its own OAuth token.

The key separationThe model selects a partner name and proposes tool calls; it never receives a raw HTTP client or token. The graph resolves the partner through PartnerRegistry, filters the plan, and invokes only that client's MCP interface.

Classification happens before partner lookup. That single decision determines which MCP catalog, credentials, and workspace boundary are used for the rest of the request.

Bounded re-planning is intentionalAfter each execution, the graph returns to plan_tools. Previous calls and results let the model perform dependent work such as discover access, search, then fetch. The total across all rounds cannot exceed max_mcp_tool_calls.

4. Four useful execution paths

General

"Hello"

classify → general → END

No partner registry lookup and no MCP connection.

Notion read

"Find our laptop policy"

Defaults an ambiguous knowledge/page request to Notion, discovers Notion tools, executes read calls, then synthesizes.

Linear read

"List issues in the next cycle"

The issue/cycle vocabulary routes to Linear. Only the Linear catalog and token are used.

Partner write

"Create a Linear issue"

The first run returns approval_required=true plus planned_tools. Approval resubmits the request with approve_write=true; classification and planning run again before execution.

Current scope: one partner per requestRouteDecision.partner is a single string, not a list. A request that needs both Notion and Linear is not orchestrated across both systems in one graph invocation.

8. Key concepts, in plain language

Partner routing

Turning one user request into a domain choice. Here the domain is exactly one of Notion or Linear, encoded in a validated route object.

Registry pattern

A central name-to-object map. The graph asks for partners.get(name) instead of knowing how every partner client is built.

MCP

A standard protocol for initialization, capability discovery (tools/list), and invocation (tools/call). It separates agent logic from vendor-specific APIs.

Structured Outputs

JSON Schema constrains the model's response shape; Pydantic validates it again. Natural language becomes branchable program data.

OAuth + PKCE

The operator authorizes a partner without handing the app a password. The code/verifier exchange yields scoped, refreshable credentials.

Human in the loop

A write route ends before execution until the caller explicitly resubmits with consent. Confidence is never treated as approval.

Grounding

The final workspace answer is generated after tool execution, with the MCP results included. This reduces unsupported claims but is not a mathematical guarantee.

Checkpoint vs chat memory

MemorySaver stores graph state by thread in this process. The prompts still use the current message, not a full conversational history.

9. Guarantees and security boundaries

MechanismWhat it gives youWhat it does not give you
Partner enumThe model cannot emit an arbitrary partner name in a valid route.Correct semantic routing every time.
Registry isolationDifferent URLs and token files per partner.Per-end-user credential isolation.
Live tool filterInvented tool names are removed.Safe or authorized arguments.
READ write-name filterKnown write-like names are blocked twice.Detection of every possible side effect.
Approval gateA classified WRITE route stops before tool execution without consent.Protection if the classifier incorrectly labels a write as READ and the name heuristic misses it.
Call budgetAt most the configured total MCP calls per invocation.Global quotas or cost controls.
OAuthCalls use saved authorization for the selected partner.Tenant authorization or application user authentication.
MemorySaverThread checkpoints during one process lifetime.Restart safety, replica sharing, or durable audit.
Production priorityReplace local token files with encrypted, per-user/per-tenant storage; authenticate the FastAPI caller; use an explicit reviewed tool allowlist with READ/WRITE metadata; and add durable audit, idempotency, and database checkpoints.

10. Adding another hosted MCP partner

The registry removes graph duplication, but adding a partner is not completely plug-and-play because routing vocabulary and settings still need deliberate updates.

  1. Add URL and token-file fields to Settings and .env.example.
  2. Add a PartnerSpec entry with its display name and setting-field names.
  3. Reuse SingleMethodOAuthClientProvider, or supply a compatible provider class if the server differs.
  4. Update classifier instructions with the new partner's domain vocabulary and ambiguity rules.
  5. Add a convenience auth wrapper only if desired; the generic partner_auth script already supports registered names.
  6. Add registry, routing, approval, and status tests for the partner.
Do not skip policy reviewA new live catalog can introduce tool names the substring heuristic does not understand. Production onboarding should attach explicit risk and authorization metadata to every allowed tool.

Debug in decision order

  1. Check /v1/status for the OpenAI key and the selected partner's token-file presence.
  2. Inspect partner, intent, and trace_id in the response.
  3. Wrong partner: inspect classifier instructions/output. Right partner but wrong action: inspect the live tool list and planner.
  4. Approval surprise: compare route risk, selected tool names, and require_write_approval.
  5. Access failure: run the partner-specific authorization command, then retry.
