Invoke Notion MCP from Postman

Learn what every request does, why it exists, how OAuth identifies you as the Notion user Santhosh, and how a raw HTTP client moves from “not authenticated” to calling real Notion tools.

Start here

The mental model

Postman is pretending to be a small MCP client. It first gets permission from Notion, then starts the MCP protocol, discovers available tools, and finally invokes one of those tools.

1

OAuth answers “who and may they enter?”

You sign in on Notion's website. Notion records your consent and issues tokens tied to your user and workspace.

2

MCP answers “what can this server do?”

The client initializes the protocol and asks the server for its live list of tools and their argument schemas.

3

A tool call performs the work

The client sends a structured tools/call request such as search, fetch, create, or update.

MCP is not the Notion REST API.MCP is a standard protocol designed for AI clients to discover and invoke tools. It uses JSON-RPC messages carried over HTTP. The server may internally use Notion services, but you interact with named MCP tools rather than hard-coded REST resources.
Identity

How does Notion know “I am Santhosh”?

Your name is not placed in the JSON body. Notion learns your identity during the browser-based OAuth login, then links the resulting access token to your Notion user and the workspace you authorized.

Identity chain
Notion login sessionSanthosh's account
→
OAuth grantuser_id + workspace_id + consent
→
Bearer access tokenopaque credential sent by Postman

client_id identifies the application

It says “this request comes from the Postman client registration.” It does not mean Santhosh.

access_token represents the authorized connection

Notion resolves it to the authorizing user, workspace, permissions, and consent. Treat it like a password.

You never send your Notion password to Postman.You enter it only on Notion's own authorization page. Postman receives a temporary authorization code and exchanges that code for tokens.

A successful initial token exchange can include user_id, workspace_id, and email_domain. Those fields let an application associate the connection with the correct user and tenant. Refresh responses may omit these identity fields, so production applications store them from the initial exchange.

Important distinction

Why OAuth instead of Basic, API keys, or “Bearer”?

OAuth and Bearer are not alternatives.OAuth is the authorization process used to obtain and renew an access token. Bearer describes how that access token is sent afterward: whoever bears the token can use it.
MethodWhat is sentWhy it is or is not appropriate here
OAuth 2.0 + PKCEUser signs in and consents; client receives short-lived access and refresh tokens.Best fit for user-delegated access. Supports consent, revocation, workspace selection, expiring tokens, and separate identities for each user.
Bearer tokenAuthorization: Bearer <access_token>This is how the OAuth access token is presented to MCP. It does not explain how the token was safely issued.
Basic authenticationUsually username and password encoded in an HTTP header.Would expose a long-lived password to the client and cannot naturally express workspace consent or delegated access. Not supported by hosted Notion MCP.
API key / personal tokenA manually created long-lived secret.Useful for some server-to-server APIs, but hosted Notion MCP currently requires interactive OAuth. A normal Notion integration token is not a substitute.
CookieBrowser session cookie.Designed for browser sessions, vulnerable if copied, and not an MCP client credential. Never copy your Notion cookies into Postman.
mTLS / signed JWTMachine certificate or signed machine assertion.Useful in specialized enterprise machine-to-machine systems, but it does not provide the interactive user consent flow required by hosted Notion MCP.

Why PKCE?

PKCE protects the temporary authorization code from interception. Postman creates a random secret called a code_verifier, hashes it into a code_challenge, and sends only the challenge during authorization. When exchanging the returned code, Postman must present the original verifier. A thief who steals only the code cannot redeem it without the verifier.

code_verifier  = random secret kept by Postman
code_challenge = BASE64URL(SHA256(code_verifier))

Authorization request sends: code_challenge
Token request later sends:    code_verifier
Preparation

Before opening Postman

  • You can sign in to the intended Notion account in a browser.
  • You know which Notion workspace you want to authorize.
  • Your workspace administrator allows the Postman/custom MCP client if MCP governance is enabled.
  • You have a current Postman desktop or web client capable of OAuth 2.0 Authorization Code with PKCE.
  • You will use a non-sensitive test page before trying create or update operations.
Do not paste real tokens into screenshots, source control, chat, or shared Postman collections.Store secrets only in a private/local Postman environment. A bearer token is usable by anyone who obtains it.

Optional but educational

Step 1 — Discover OAuth configuration

Real MCP SDKs do not have to hard-code OAuth endpoints. They discover which authorization server protects the MCP resource and then download its metadata. In Postman, these two read-only requests help you understand the process.

1A
GETNo authentication

Protected-resource metadata

GET https://mcp.notion.com/mcp/.well-known/oauth-protected-resource
Why: This tells the client which OAuth authorization server protects the MCP endpoint. Do not assume authentication always lives on the same hostname as the resource.
1B
GETNo authentication

Authorization-server metadata

GET https://mcp.notion.com/.well-known/oauth-authorization-server

The response advertises values such as:

{
  "issuer": "https://mcp.notion.com",
  "authorization_endpoint": "https://mcp.notion.com/authorize",
  "token_endpoint": "https://mcp.notion.com/token",
  "registration_endpoint": "https://mcp.notion.com/register",
  "scopes_supported": ["default"],
  "code_challenge_methods_supported": ["plain", "S256"]
}
Why: Metadata prevents endpoint guessing, advertises supported grants and PKCE methods, and lets clients adapt if configuration changes.
OAuth setup

Step 2 — Register Postman as a client

Notion supports Dynamic Client Registration (DCR). The registration describes the client and locks in the exact redirect URI. Registration identifies the software; it does not authorize Santhosh yet.

2
POSTJSONNo user token

Register the OAuth client

POST {{oauth_register_url}}
Content-Type: application/json
Accept: application/json

{
  "client_name": "Postman Notion MCP - Santhosh",
  "client_uri": "https://www.postman.com/",
  "redirect_uris": ["{{redirect_uri}}"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none",
  "scope": "default"
}
client_name
A human-readable application label shown in connection/admin screens. It is not your user identity.
client_uri
Information URL for the client. It helps users/admins understand what is connecting.
redirect_uris
Exact allowlist of callback URLs. OAuth rejects mismatches to stop an attacker redirecting the authorization code elsewhere.
grant_types
authorization_code permits initial login; refresh_token permits renewal.
response_types
code requests a temporary one-time code, not a token placed in the browser URL.
token_endpoint_auth_method
none means this public client relies on PKCE instead of a client secret it could not safely protect.
scope
default is the scope currently advertised by Notion's MCP authorization server.

Copy the returned client_id into the Postman environment. If the response also contains a client_secret, keep it private and follow the returned authentication method; do not invent a secret.

Do not register on every normal API call.Register once and reuse the client registration. Re-register only when the client metadata or redirect URI must change, or when the registration is lost/revoked.

3

Click “Get New Access Token”

  1. Postman generates state, code_verifier, and code_challenge.
  2. A browser opens /authorize.
  3. Sign in to Notion as Santhosh. If the wrong account appears, switch accounts before consenting.
  4. Select/confirm the intended workspace and approve access.
  5. Notion redirects to Postman's callback with a short-lived code and the original state.
  6. Postman validates state, then sends the code plus code_verifier to /token.
  7. Notion returns an access token, usually a refresh token, expiry details, and initial identity fields.
  8. Click Use Token.
This is the moment Notion learns you are Santhosh.The browser login identifies your Notion account; the consent records the chosen workspace; the resulting token represents that authorized connection.

What the token request conceptually contains

POST https://mcp.notion.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=<one-time-code>
&client_id=<registered-client-id>
&redirect_uri=https%3A%2F%2Foauth.pstmn.io%2Fv1%2Fbrowser-callback
&code_verifier=<secret-created-by-postman>

The authorization code is intentionally short-lived and single-use. The access token should never appear in the browser address bar.

Step 4 — Initialize the MCP protocol

Authentication is now complete, but the MCP conversation has not started. The initialize request negotiates a protocol revision and announces basic client capabilities.

4A
POSTJSON-RPC 2.0Bearer token

Send initialize

POST {{mcp_url}}
Authorization: Bearer {{access_token}}
Content-Type: application/json
Accept: application/json, text/event-stream

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": {},
    "clientInfo": {
      "name": "postman-notion-mcp-guide",
      "version": "1.0.0"
    }
  }
}
Authorization
The OAuth bearer token proves the request belongs to the authorized connection.
Accept
MCP Streamable HTTP may reply as regular JSON or as a Server-Sent Events stream; advertise both.
jsonrpc
Declares the JSON-RPC 2.0 message format.
id
Correlates a response with this request. Reuse is confusing; increment it for each request.
method
The MCP operation. initialize must happen before ordinary tools in the handshake-era protocol.
protocolVersion
The newest handshake-era revision this manual client proposes. Accept the server-returned version and use it later.
capabilities
Features the client offers to the server. Empty is appropriate for this basic Postman exercise.
clientInfo
Diagnostic software name/version—not the human user identity.
If Notion returns a different protocol version, that is negotiation.Set {{mcp_protocol_version}} to the value in result.protocolVersion. If your environment rejects 2025-11-25, retry with 2025-06-18; an MCP SDK normally handles this automatically.

Also inspect the response headers. If present, save Mcp-Session-Id into {{mcp_session_id}}. Notion describes this value as opaque: do not decode it or attach business meaning to it.

4B
POSTNotification

Send notifications/initialized

POST {{mcp_url}}
Authorization: Bearer {{access_token}}
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: {{mcp_protocol_version}}
Mcp-Session-Id: {{mcp_session_id}}

{
  "jsonrpc": "2.0",
  "method": "notifications/initialized"
}
Why: The client acknowledges that it received the initialize result and is ready. A notification has no id, so the server does not owe it a JSON-RPC result. An empty body or HTTP 202 is normal.

If no session header was returned, omit Mcp-Session-Id rather than sending an empty value.

Optional Postman test script to capture values

Add this to the initialize request's Tests / Post-response tab:

const sessionId = pm.response.headers.get("Mcp-Session-Id");
if (sessionId) pm.environment.set("mcp_session_id", sessionId);

let raw = pm.response.text().trim();
if (raw.startsWith("event:") || raw.includes("\ndata:")) {
  const dataLine = raw.split(/\r?\n/).find(line => line.startsWith("data:"));
  if (dataLine) raw = dataLine.slice(5).trim();
}

try {
  const message = JSON.parse(raw);
  const version = message?.result?.protocolVersion;
  if (version) pm.environment.set("mcp_protocol_version", version);
} catch (error) {
  console.warn("Could not parse initialize response", error);
}
Useful work

Step 5 — Discover and call Notion tools

5A
POSTRead-only discovery

List tools

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {}
}
Why: Tool availability and input schemas can change by server version, workspace, permission, and plan. A real MCP client discovers the live contract instead of hard-coding assumptions.

Each returned tool includes a name, description, and inputSchema. The input schema is the authoritative description of required and optional arguments.

5B
POSTTool call

Check tool access

{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "notion-get-tool-access",
    "arguments": {}
  }
}
Why: Notion recommends checking this map before conditionally available tools. It explains whether capabilities are available, restricted, or require another plan/configuration.
5C
POSTRead operation

Search Notion

{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "tools/call",
  "params": {
    "name": "notion-search",
    "arguments": {
      "query": "Partner Agent architecture"
    }
  }
}

If notion-search is not listed, use the search tool actually returned by tools/list—for example, your connection may expose notion-ai-search. Match its exact inputSchema.

5D
POSTGeneric template

Call any discovered tool

{
  "jsonrpc": "2.0",
  "id": 5,
  "method": "tools/call",
  "params": {
    "name": "<exact name from tools/list>",
    "arguments": {
      "<field from inputSchema>": "<value>"
    }
  }
}
Pause before write tools.Create, update, move, comment, and similar operations can change real workspace data. Read the tool description and schema, test in a sandbox page, and require human confirmation in production systems.

Headers for requests after initialization

Authorization: Bearer {{access_token}}
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: {{mcp_protocol_version}}
Mcp-Session-Id: {{mcp_session_id}}   # only if initialize returned one

Understanding tool results

A successful HTTP response can still contain a tool-level error. Inspect both the JSON-RPC error field and the tool result's isError. Tool content is commonly an array of typed blocks such as text. Do not equate HTTP 200 with “the Notion operation succeeded.”

Token lifecycle

Step 6 — Refresh an expired access token

Access tokens expire to reduce the harm caused by accidental leakage. A refresh token lets the authorized client obtain a replacement without asking Santhosh to approve the connection every hour.

6
POSTForm URL encoded

Refresh

POST {{oauth_token_url}}
Content-Type: application/x-www-form-urlencoded
Accept: application/json

grant_type=refresh_token
&refresh_token={{refresh_token}}
&client_id={{client_id}}
Why: Short-lived access tokens limit exposure; refresh tokens preserve usability. If Notion rotates the refresh token, replace the stored old value with the new one atomically.

If refresh returns invalid_grant, the grant may be expired, revoked, already rotated, or associated with another client. Repeat interactive authorization rather than endlessly retrying.

Deep reference

Important values and what they protect

state

Prevents login CSRF and callback mix-ups. The returned value must exactly match the value stored before redirect.

code

Short-lived, single-use authorization code. It is safe to pass through the browser only because redeeming it also requires PKCE.

code_verifier

Random PKCE secret kept by the client until token exchange. Never place it in the authorization URL.

redirect_uri

Exact approved callback destination. It appears at registration, authorization, and token exchange and must match.

client_id

Public application identifier. It is not a password and does not identify the human user.

access_token

Short-lived bearer credential sent to MCP. Whoever possesses it may exercise its authorization.

refresh_token

Longer-lived, highly sensitive credential used only at the token endpoint. Never send it to the MCP endpoint.

MCP-Protocol-Version

Tells the server which MCP wire contract applies to later requests after version negotiation.

Mcp-Session-Id

Opaque correlation value returned by initialize on some servers. Echo it when supplied; do not parse it.

JSON-RPC id

Matches a response to a request. It is not a user ID, session ID, or security credential.

Fix problems

Troubleshooting

401 Unauthorized
The access token is missing, expired, malformed, revoked, or intended for a different resource. Confirm the header begins exactly with Bearer . Refresh or repeat OAuth authorization. Do not use a normal Notion REST integration token.
403 Forbidden
The token is recognized but the user/workspace lacks permission, the client is blocked by enterprise MCP governance, or a capability is unavailable. Verify Santhosh can access the page directly and ask the workspace admin whether Postman/custom MCP clients are approved.
redirect_uri mismatch
The callback must be byte-for-byte identical in registration, authorization, and token exchange. Check scheme, hostname, path, trailing slash, and URL encoding.
invalid_grant
The authorization code may be expired/reused, the PKCE verifier may not match, the redirect URI may differ, or a refresh token may be revoked/rotated. Start a fresh OAuth flow and avoid replaying old values.
Unsupported protocol version
Use the version returned by the server. For manual handshake testing, try 2025-11-25, then 2025-06-18 if required. Production clients should use a current MCP SDK for automatic negotiation.
Response looks like “event: message / data: ...”
This is Server-Sent Events framing, not corrupted JSON. Read the JSON after data:. Keep both application/json and text/event-stream in the Accept header.
Method not found or invalid arguments
Run tools/list again. Copy the exact tool name and follow its returned inputSchema. Tool contracts should not be guessed from old examples.
Search cannot find a page
Confirm the authorizing Notion user can access it, the correct workspace was selected, and the active token belongs to that connection. Authentication cannot grant permissions that Santhosh does not already have.
Postman sends the wrong account's token
Delete or deselect the saved OAuth token, switch Notion accounts in the authorization browser, authorize again, and use separate Postman environments for separate people/workspaces.
Safety

Security checklist

  • Keep access tokens, refresh tokens, client secrets, and PKCE verifiers out of Git and shared collections.
  • Use HTTPS only; never disable TLS certificate verification for real credentials.
  • Use S256 PKCE, validate state, and require exact redirect URI matching.
  • Store production tokens encrypted server-side, indexed by application user, partner, and workspace.
  • Do not log Authorization headers or complete token responses.
  • Separate read tools from write tools; ask for explicit confirmation before mutations.
  • Revoke the Notion connection immediately if a token or exported Postman environment leaks.
  • Do not let one employee's token become a shared company credential.

Glossary

Terms in plain English

MCP

A standard way for AI clients to discover and invoke tools or retrieve context from servers.

JSON-RPC

A message format with request IDs, method names, parameters, results, and errors.

Streamable HTTP

MCP's recommended remote HTTP transport, able to return JSON or an event stream.

OAuth 2.0

A delegated authorization framework: a user grants an application limited access without sharing their password.

PKCE

A proof that the client exchanging the code is the same client that started authorization.

DCR

Dynamic Client Registration: the client registers itself through an API and receives a client ID.

Scope

A label describing requested authorization. Notion MCP currently advertises default.

Bearer credential

A secret accepted based on possession. It must be protected in storage, transit, and logs.

  2. Read OAuth discovery metadata.
  3. Register the Postman callback and save client_id.
  4. Use Authorization Code with PKCE to sign in as Santhosh and authorize the intended workspace.
